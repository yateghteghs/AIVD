# AI Voter Desk (AIVD)

**Index Prima · AI4Elections prototype · Rise Networks hackathon (sprint 28 Nov – 13 Dec 2026)**

AI Voter Desk answers voter questions in **English and Nigerian Pidgin**. Answers cite the **Electoral Act 2026** and, where it helps, INEC's own guideline documents. It:

- answers only from official text that ships with the app (the Act, plus INEC's 2026 Regulations and Guidelines and other INEC guidance), and shows the section or paragraph, page and quoted wording;
- says **"Not covered"** when the loaded provisions don't clearly settle the question, instead of guessing;
- **refuses** to give voting advice ("who should I vote for?"), make predictions ("who will win?"), or help with manipulation (rigging, vote buying, intimidation, fake results, misinformation), while still answering legal questions about those topics ("is vote buying an offence?");
- shows a **rule-conflict panel** for Section 47(3): the Act's "cancel and re-run within 24 hours" rule next to the 2026 Regulations' "continue the following day" rule (paras. 26, 65, 66), which one controls, and why;
- has **👍/👎** and a **Flag for review** button on every answer;
- has a **Review Desk** at `/admin` for your team (invite-only), showing usage, unanswered questions, unhelpful answers, refusals and flags to triage. Voters never log in.

> **Status (18 Nov 2026):** `data/provisions.js` holds the **official Electoral Act 2026** (156 sections, 457 records), ingested from INEC's PDF. `data/guidelines.js` holds **216 passages from 5 INEC documents** listed at <https://inecnigeria.org/elections/guidelines>. Three of those documents are scans, so their text came from OCR: the paragraphs used in the conflict panel were checked against the page images, but the rest still need proofreading (see [INEC guidance](#inec-guidance-documents)).

## Quick start

No build step and no dependencies. The app runs entirely in the browser.

```bash
cd ai4elections-prototype
```

```bash
python3 -m http.server 8080
```

Then open <http://localhost:8080>. You can also open `index.html` directly from disk. To pre-fill a question, add `?q=` to the URL, for example `index.html?q=Can%20my%20brother%20collect%20my%20PVC`.

Run the tests (Node 18+ and Python 3.9+):

```bash
npm test
```

## Deploying (Vercel + Supabase)

The app is a static site. **Vercel** hosts it and redeploys on every push. **Supabase** is optional and powers the shared review queue: without it, flags stay in each viewer's browser.

### Vercel (one-time, about 3 minutes)

1. Go to <https://vercel.com/new>, sign in with GitHub, and **Import** `yateghteghs/AIVD`. If the repo isn't listed, grant the Vercel GitHub app access to it.
2. Leave **Root Directory** as the repo root and **Framework Preset** as "Other". `/vercel.json` already sets the build (`node ai4elections-prototype/scripts/build_web.js`) and the output directory (`dist`).
3. Click **Deploy**. You get a `*.vercel.app` URL. Every later push to the branch deploys automatically: pushes to the production branch update the main URL, and other branches get preview URLs.
4. Production branch: Vercel uses the repo's default branch. To make this work branch production, set it under **Project → Settings → Git → Production Branch**, or merge it into `main`.

### Supabase (shared review queue)

1. Create a project at <https://supabase.com/dashboard>. The free tier is enough.
2. Open **SQL Editor → New query**, paste `supabase/schema.sql`, and click **Run**. This creates the `flags` table with row-level security: the public app can only *insert* flags, never read or change them.
3. Under **Project Settings → API**, copy the **Project URL** and the public key: either the **publishable** key (`sb_publishable_…`) or the legacy **anon public** key (`eyJ…`). Both work.
4. In Vercel, go to **Project → Settings → Environment Variables** and add `SUPABASE_URL` and `SUPABASE_ANON_KEY`, then redeploy (**Deployments → ⋯ → Redeploy**).
5. Flags now show "Sent to the review team". Reviewers read them in Supabase under **Table Editor → flags** (filter by `status`, set `reviewer`/`resolution`, export CSV).

Never put the **service_role** key anywhere in this project. Only the anon key belongs in Vercel.

`scripts/build_web.js` copies only the browser files (`index.html`, `engine.js`, `data/*.js`) into `dist/` and writes `config.js` from the environment variables, so no keys are committed and tests and scripts are not published.

## Review Desk (admin dashboard)

`/admin` is for your review team only. Voters never see it or log in. It shows:

- totals for the chosen period (7 days, 30 days or all time): questions, % answered / not covered / refused, % in Pidgin, % rated helpful, open flags;
- questions per day, stacked by outcome (hover for numbers, or "Show as table");
- the most-asked questions AIVD couldn't answer, which is your to-do list for the corpus;
- the latest 👎 answers and refusals (check refusals for false positives);
- flags to triage: set the status (Open / Needs test / Resolved / Won't fix), add a resolution note, and save;
- a CSV download of the questions.

Open `/admin?demo` to see it with generated sample data, no Supabase needed.

**Privacy.** The voter app logs each question with how it was answered (type, citations, language), plus any 👍/👎 linked by a random ID. It stores no names, accounts or IP addresses, and the page asks voters not to type personal details. The public key can only *add* rows; it can never read them back.

**One-time setup in Supabase** (after the Vercel/Supabase steps under *Deploying*):

1. **SQL Editor → New query**: paste `supabase/002_dashboard.sql` and click **Run**. It is safe to run more than once.
2. **Authentication → URL Configuration**: set **Site URL** to your Vercel address (e.g. `https://ai-voter-desk.vercel.app`) and add `https://ai-voter-desk.vercel.app/admin` under **Redirect URLs**.
3. **Authentication → Sign In / Providers**: turn **off** "Allow new users to sign up". Only people you invite get accounts. Even if someone does sign up, they can't see any data unless step 5 adds them.
4. **Authentication → Users → Invite user**: enter each reviewer's email.
5. **SQL Editor**: add each invited reviewer to the reviewer list:
   ```sql
   insert into public.reviewers (user_id, email)
   select id, email from auth.users where email = 'reviewer@example.org'
   on conflict do nothing;
   ```
6. The reviewer opens `/admin`, enters their email and clicks the emailed sign-in link.

To remove a reviewer: `delete from public.reviewers where email = '…';`.

Check the security rules locally at any time (needs PostgreSQL installed):

```bash
bash supabase/tests/run.sh
```

## How an answer is produced

1. **Language.** Weighted Pidgin markers (`wetin`, `dey`, `abeg`, `di`, `una`, …) decide between `en` and `pcm`. The header toggle (Auto / English / Pidgin) can override this.
2. **Guardrails** (`data/rules.js`) run first, in this order: manipulation, then voting advice, then prediction. Each has `allow` patterns so that informational questions ("what is the penalty for…", "how do I report…") are not refused.
3. **Retrieval.** BM25 runs over title, text and keywords, with a small Pidgin-to-English expansion lexicon. A provision is used only if its score is at least `minScore` and at least `minCoverage` of the question's content words match. Otherwise the answer is **Not covered**.
4. **Answer.** If a reviewed summary exists (`summary_en` / `summary_pcm`), it is shown. Otherwise AIVD names the most relevant section and quotes the official wording. Up to 3 citations are listed, each with an excerpt and a page number.
5. **INEC guidance.** The same search runs over the guidance corpus. Current (2026) documents are shown as supporting citations under the Act. If the Act doesn't settle a question but current guidance does (for example, phones in the voting cubicle), AIVD answers from the guidance and says so. **Dated** documents (written for the 2022 Act or the 2023 election) are only ever shown as extra reading, never as the sole basis for an answer.
6. **Conflicts.** If a cited provision or guidance paragraph triggers a conflict record (currently s.47(3) and Regulations paras. 26, 65 and 66), the panel appears. Its source texts are pulled live from the corpora, so they always match the citations.

There is no LLM in the loop, so every sentence shown is either fixed template text or wording from the corpus. An LLM layer for rephrasing could be added later behind the same guardrails and citation checks.

## Loading the official Electoral Act 2026

The PDF is published by INEC. Source PDFs live in `sources/`, which is git-ignored.

```bash
mkdir -p sources && curl -L -o sources/Electoral-Act-2026.pdf https://inecnigeria.org/documents/Electoral-Act-2026.pdf
```

```bash
python3 scripts/ingest_act.py sources/Electoral-Act-2026.pdf --report ingest-report.json
```

```bash
npm test
```

The script:

- detects the right-hand column of marginal notes (section headings printed in the margin) and extracts only the body text beside it, so headings don't get mixed into the legal wording;
- strips running headers, footers and page numbers;
- skips the "Arrangement of Sections" table of contents (the body starts at "ENACTED" / "[Commencement]");
- splits the Act into sections and subsections (`s47-3`), takes section titles from the Arrangement of Sections, and keeps Part headings and page numbers;
- stops at the Schedules;
- tags topics, merges reviewed summaries from `data/summaries.json` and keywords from `data/keywords.json`, and writes `data/provisions.js` with `verified: true` and the PDF's SHA-256.

It then prints the section range, any **gaps** in numbering, missing titles, and suspiciously short or long records.

**After ingesting:**

1. Read the anomaly report. Spot-check at least 10 sections against the PDF, including all of s.47.
2. If marginal notes come out wrong, re-run with `--layout`. If real sections are being skipped, adjust `--max-gap`.
3. If the PDF is scanned (the script will say so), run `ocrmypdf in.pdf out.pdf` first and check the OCR output closely.
4. Re-run `npm test`.
5. Add reviewed summaries for the sections used in the demo script to `data/summaries.json`, then re-ingest.

## INEC guidance documents

```bash
python3 scripts/ingest_guidelines.py --src-dir sources --download
```

The script downloads the PDFs listed in `scripts/guidelines_manifest.json` (from <https://inecnigeria.org/elections/guidelines>), then:

- uses the text layer when there is one, and otherwise OCRs each page with Tesseract (`apt-get install tesseract-ocr`), caching results in `sources/.ocr/`. OCR of all 66 scanned pages takes about 30 seconds on 4 cores;
- drops the right-hand marginal-note column, and uses those notes as paragraph titles;
- runs a second, digits-only OCR pass over the paragraph-number column, because full-page OCR sometimes drops or misreads numbers (e.g. "77." read as "TT.");
- splits numbered documents into paragraphs (long ones into lettered sub-items, e.g. `para. 21(f)`), and other documents into chunks of a few hundred characters;
- applies corrections and proofreading records from `data/proofread.json`.

| Document | Year | Status | Text | Records |
|---|---|---|---|---|
| Regulations and Guidelines for the Conduct of Elections, 2026 | 2026 | current | OCR (scanned) | 123 (paras. 1–117) |
| Procedure for Electronic Transmission & Collation of Results | 2022 | dated | text layer | 14 |
| 2023 General Election Voting Procedures | 2023 | dated | text layer | 6 |
| Press release: Conduct of Supplementary Elections (Mar 2023) | 2023 | dated | OCR | 4 |
| Revised Framework and Regulations for IDP Voting, 2022 | 2022 | dated | OCR | 69 |

**Proofreading OCR text.** Every OCR'd record shows "Scanned text, not yet proofread" in the app until it is checked. To check one, compare it word for word with the PDF page (the citation links straight to it). Add an entry to `data/proofread.json` with any corrected `text`/`title`, your name and the date, set `"verified": true`, and re-run the script. Paras. 26, 65 and 66, which the conflict panel quotes, have had an AI-assisted check against the page images and still need a human to confirm them.

## Review queue

Every flag is saved in the browser's `localStorage` (shown under **Review queue**, exportable as JSON). When Supabase is configured, it is also sent to the shared `flags` table and appears in the Review Desk. A 👎 opens the flag form so the voter can say what was wrong. Each record contains the question, detected language, answer type, citations, the reviewer's category and note, and the corpus version. Use it during user testing.

## Known limitations

- **OCR'd guidance needs proofreading.** Apart from paras. 26, 65 and 66, the Regulations 2026 text is unproofread OCR and is labelled that way in the app.
- **The conflict analysis needs legal review.** The "where they can differ" text is AIVD's reading of the three sources (`reviewed: false` in `rules.js`).
- **Dated documents** (2022–2023) are kept for reference and clearly marked. They are never used as the only basis for an answer.
- **Pidgin** answer text and UI strings were written for the prototype and need a native-speaker review. Quoted provisions stay in official English.
- **Guardrails are pattern-based.** Run the review queue and add patterns plus test cases for anything that slips through. Never remove an `allow` pattern without adding a test.
- **Retrieval is lexical.** Paraphrases far from the Act's wording may come back as "Not covered". That is the safe failure, but log those cases via flags.
- **The conflict panel** covers only s.47(3).
