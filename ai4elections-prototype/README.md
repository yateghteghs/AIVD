# AI Voter Desk (AIVD)

**Index Prima · AI4Elections prototype · Rise Networks hackathon (sprint 28 Nov – 13 Dec 2026)**

AI Voter Desk answers voter questions in **English and Nigerian Pidgin**. Every answer cites a provision of the **Electoral Act 2026**. It:

- answers only from provision text that ships with the app, and shows the section, page and quoted wording;
- says **"Not covered"** when the loaded provisions don't clearly settle the question, instead of guessing;
- **refuses** to give voting advice ("who should I vote for?"), make predictions ("who will win?"), or help with manipulation (rigging, vote buying, intimidation, fake results, misinformation), while still answering legal questions about those topics ("is vote buying an offence?");
- shows a **rule-conflict panel** for Section 47(3), with the Act and INEC's Regulations side by side, which one controls, and why;
- has a **Flag for review** button on every answer. Flags go into a review queue that can be exported as JSON.

> ⚠️ **Status: the corpus is SAMPLE text.** `data/provisions.js` currently holds unverified plain-language placeholders, not the official wording. A yellow banner in the app says so. Before any public demo, run the ingest script on the official PDF (see below) so the banner turns green.

## Quick start

No build step and no dependencies. The app runs entirely in the browser.

```bash
cd ai4elections-prototype
```

```bash
python3 -m http.server 8080
```

Then open <http://localhost:8080>. You can also open `index.html` directly from disk. To pre-fill a question, add `?q=` to the URL, for example `index.html?q=Can%20my%20brother%20collect%20my%20PVC`.

Run the tests (Node 18+ and Python 3.9+):

```bash
npm test
```

## Deploying (Vercel + Supabase)

The app is a static site. **Vercel** hosts it and redeploys on every push. **Supabase** is optional and powers the shared review queue: without it, flags stay in each viewer's browser.

### Vercel (one-time, about 3 minutes)

1. Go to <https://vercel.com/new>, sign in with GitHub, and **Import** `yateghteghs/AIVD`. If the repo isn't listed, grant the Vercel GitHub app access to it.
2. Leave **Root Directory** as the repo root and **Framework Preset** as "Other". `/vercel.json` already sets the build (`node ai4elections-prototype/scripts/build_web.js`) and the output directory (`dist`).
3. Click **Deploy**. You get a `*.vercel.app` URL. Every later push to the branch deploys automatically: pushes to the production branch update the main URL, and other branches get preview URLs.
4. Production branch: Vercel uses the repo's default branch. To make this work branch production, set it under **Project → Settings → Git → Production Branch**, or merge it into `main`.

### Supabase (shared review queue)

1. Create a project at <https://supabase.com/dashboard>. The free tier is enough.
2. Open **SQL Editor → New query**, paste `supabase/schema.sql`, and click **Run**. This creates the `flags` table with row-level security: the public app can only *insert* flags, never read or change them.
3. Under **Project Settings → API**, copy the **Project URL** and the public key: either the **publishable** key (`sb_publishable_…`) or the legacy **anon public** key (`eyJ…`). Both work.
4. In Vercel, go to **Project → Settings → Environment Variables** and add `SUPABASE_URL` and `SUPABASE_ANON_KEY`, then redeploy (**Deployments → ⋯ → Redeploy**).
5. Flags now show "Sent to the review team". Reviewers read them in Supabase under **Table Editor → flags** (filter by `status`, set `reviewer`/`resolution`, export CSV).

Never put the **service_role** key anywhere in this project. Only the anon key belongs in Vercel.

`scripts/build_web.js` copies only the browser files (`index.html`, `engine.js`, `data/*.js`) into `dist/` and writes `config.js` from the environment variables, so no keys are committed and tests and scripts are not published.

## How an answer is produced

1. **Language.** Weighted Pidgin markers (`wetin`, `dey`, `abeg`, `di`, `una`, …) decide between `en` and `pcm`. The header toggle (Auto / English / Pidgin) can override this.
2. **Guardrails** (`data/rules.js`) run first, in this order: manipulation, then voting advice, then prediction. Each has `allow` patterns so that informational questions ("what is the penalty for…", "how do I report…") are not refused.
3. **Retrieval.** BM25 runs over title, text and keywords, with a small Pidgin-to-English expansion lexicon. A provision is used only if its score is at least `minScore` and at least `minCoverage` of the question's content words match. Otherwise the answer is **Not covered**.
4. **Answer.** If a reviewed summary exists (`summary_en` / `summary_pcm`), it is shown. Otherwise AIVD names the most relevant section and quotes the official wording. Up to 3 citations are listed, each with an excerpt and a page number.
5. **Conflicts.** If a cited provision triggers a conflict record (currently `s47-3`), the panel appears. Its Act-side text is pulled live from the corpus, so it always matches the citation.

There is no LLM in the loop, so every sentence shown is either fixed template text or wording from the corpus. An LLM layer for rephrasing could be added later behind the same guardrails and citation checks.

## Loading the official Electoral Act 2026

```bash
python3 scripts/ingest_act.py path/to/Electoral-Act-2026.pdf --report ingest-report.json
```

```bash
npm test
```

The script:

- extracts text page by page (`pdftotext`, falling back to `pdfplumber`);
- strips running headers, footers and page numbers;
- skips the "Arrangement of Sections" table of contents (the body starts at "ENACTED" / "[Commencement]");
- splits the Act into sections and subsections (`s47-3`) and keeps Part headings, marginal notes and page numbers;
- stops at the Schedules;
- tags topics, merges reviewed summaries from `data/summaries.json`, and writes `data/provisions.js` with `verified: true` and the PDF's SHA-256.

It then prints the section range, any **gaps** in numbering, missing titles, and suspiciously short or long records.

**After ingesting:**

1. Read the anomaly report. Spot-check at least 10 sections against the PDF, including all of s.47.
2. If marginal notes come out wrong, re-run with `--layout`. If real sections are being skipped, adjust `--max-gap`.
3. If the PDF is scanned (the script will say so), run `ocrmypdf in.pdf out.pdf` first and check the OCR output closely.
4. In `data/rules.js`, replace the INEC Regulations placeholder in `conflict-s47-3` with the exact clause and edition. Rewrite `tension` from the real texts, then set `verified: true`.
5. Re-run `npm test`. Retrieval thresholds (`minScore`, `minCoverage` in `engine.js`) were tuned on the 12-item sample corpus. Expect to re-tune them against the full Act, and update `topic` expectations or `scripts/topic_map.json` where the real sections are tagged differently.
6. Add reviewed summaries for the sections used in the demo script to `data/summaries.json`, then re-ingest.

## Evaluation set

`tests/questions.json` has 50 questions:

| Group | Cases | What it checks |
|---|---|---|
| `en-*` | 17 | English questions answered with a citation on the right topic |
| `pcm-*` | 8 | Pidgin questions detected as Pidgin and answered on the right topic |
| `nc-*` | 8 | Out-of-scope questions return **Not covered** |
| `adv-*` | 6 | Voting-advice refusals |
| `pred-*` | 4 | Prediction refusals |
| `man-*` | 7 | Manipulation refusals, plus one "how do I report vote buying" case that must **not** be refused |

Cases about Section 47(3) also require the conflict panel to show.

```bash
node tests/run.js --verbose
```

```bash
node tests/run.js --only pcm
```

```bash
node tests/run.js --json eval-results.json
```

The current result is **50/50 on the sample corpus**. That figure says the pipeline and guardrails behave as designed. It does not measure answer quality on the real Act, and the test set and thresholds were developed together, so expect some failures after ingest and add new held-out questions as the team finds gaps.

## Review queue

Every flag is saved in the browser's `localStorage` (shown under **Review queue**, exportable as JSON). When Supabase is configured, it is also sent to the shared `flags` table (see Deploying). Each record contains the question, detected language, answer type, citations, the reviewer's category and note, and the corpus version. Use it during user testing.

## Known limitations

- **The sample corpus is not law.** Section numbers are blank except the 47(3) slot. The 47(3) text and the INEC Regulations clause are placeholders.
- **Pidgin** answer text and UI strings were written for the prototype and need a native-speaker review. Quoted provisions stay in official English.
- **Guardrails are pattern-based.** Run the review queue and add patterns plus test cases for anything that slips through. Never remove an `allow` pattern without adding a test.
- **Retrieval is lexical.** Paraphrases far from the Act's wording may come back as "Not covered". That is the safe failure, but log those cases via flags.
- **The conflict panel** covers only s.47(3).
